## 学习内容
- 继续阅读和对比 Agentic Payment / Commerce 相关协议：
  - x402：偏 HTTP 402 / API 访问前支付，适合一次性 API、数据源、内容、推理服务的 pay-per-request。
  - MPP：偏 machine-to-machine payment coordination，适合 Agent 高频调用服务、微支付、session budget、订阅或按量结算。
  - ERC-8004：偏 Agent 身份、发现、声誉、验证注册，解决“我应该找谁、能不能信任它”的问题。
  - ERC-8183：偏 job-based commerce kernel，用 job、escrow、provider submit、evaluator complete/reject、settlement/refund 串起任务交易闭环。
  - Olas：偏已经运行的 autonomous agent economy / Mech Marketplace，提供“Agent 请求服务、Mech 离线执行、链上交付和收费”的真实案例参考。
- 结合 `tasks/week_2/payment_commerce_flow.md`，继续把“链上地址风险分析任务市场”拆成可实现的 commerce flow：
  - 用户 Agent 提出需求和预算；
  - 通过 Agent registry / reputation 找 Provider 和 Evaluator；
  - 用户钱包或 CAW 做任务级预算授权；
  - 资金进入 escrow；
  - Provider 执行并提交 deliverable hash / URI；
  - Evaluator 按 schema、deadline、证据完整性和抽样验证给出验收结果；
  - 合约根据验收结果 release、refund 或进入 dispute。

## 关键收获
- Payment 和 Commerce 不能混为一谈。x402 / MPP 更像支付入口或支付通道，解决“Agent 怎么付钱”；ERC-8183 更像任务交易内核，解决“钱什么时候释放、失败怎么退款、谁判断完成”。
- ERC-8004 更适合放在交易前置层：服务发现、身份、声誉、验证能力声明。它能降低盲选 Provider / Evaluator 的风险，但不能单独保证任务质量。
- job 的核心不是一条付款记录，而是一组可审计状态：`Open -> Funded -> Submitted -> Completed / Rejected / Expired`。只有有状态机，后续的 escrow、验收、退款和争议处理才有落点。
- receipt 应该记录关键 proof，而不是把完整报告都放链上。最小 receipt 可以包含 `job_id`、`task_hash`、`quote_hash`、`deliverable_hash`、`evaluator_attestation`、`settlement_tx_hash`。
- Olas / Mech 的启发是：Agent commerce 不一定一开始就做复杂通用市场，可以先从“明确任务请求 + 离线执行 + 链上请求/交付/收费记录”做最小闭环。

## 遇到的问题
- Evaluator 的可信度仍然是难点：单一 Evaluator 简单，但容易形成新的中心化信任点；多 Evaluator / 仲裁机制更稳，但复杂度会上升。
- 对低价 API 调用，完整 ERC-8183 escrow flow 可能太重；更合理的是 x402 / MPP 处理即时 API 付费，ERC-8183 处理需要验收的任务型交易。
- receipt 的标准化还需要继续研究：哪些字段必须上链、哪些字段只需要 IPFS / Arweave / 后端存储、哪些字段需要签名或 EIP-712 typed data。
- settlement 还需要考虑异常路径：超时未交付、交付格式错误、证据不可验证、Evaluator 拒绝但 Provider 不认可、用户对验收结果提出争议。
