### 活动二：以零知识证明的理论开始，分享各项应用（20:00–21:00）

**适合对象**：对 ZKP 基础理论和 Web3 应用场景感兴趣的开发者

核心内容：
- ZKP 核心概念：证明者（Prover）、验证者（Verifier）、完备性、可靠性、零知识性
- 主流 ZKP 方案对比：zk-SNARKs（Groth16 / PLONK）vs zk-STARKs — 信任设置、证明大小、验证成本
- Web3 应用场景全景：
  - **隐私交易**：Tornado Cash、Aztec — 隐藏发送方/接收方/金额
  - **扩容**：zk-Rollups（zkSync、StarkNet）— 链下执行+链上验证
  - **身份验证**：Polygon ID、zk-KYC — 证明"我满足条件"但不暴露具体信息
  - **跨链互操作**：zk-Bridge — 用 ZKP 验证跨链事件
  - **AI × ZKP**：zkML — 证明模型推理结果正确但不暴露模型参数或输入数据

## 💡 关键收获

1. **Hackathon 冲刺节奏（Co-learning）**：Week 4 是 Hackathon 冲刺 + Demo 准备阶段，关键是"先跑通最小闭环，再优化体验"。不需要一开始就做完整产品，能展示核心价值流就是好 MVP

2. **Payment/Commerce 方向的可落地性判断**：结合前几天的支付场景研究，Hackathon MVP 可以先做"单任务 escrow + Agent 验收 + 结果上链"的最小闭环，而不是一开始就做通用市场

3. **ZKP 理论入门**：理解了 ZKP 的三角约束（完备性、可靠性、零知识性）及其权衡。不是所有场景都需要所有三个属性——比如 Rollup 场景更看重可靠性和验证效率，零知识性反而不是核心需求

4. **ZKP 应用分层理解**：
   - Layer 1 扩容层：zk-Rollups（提升吞吐量）
   - Layer 2 隐私层：隐私交易 / 身份证明（保护用户数据）
   - Layer 3 计算验证层：zkML / zk-Oracle（验证计算正确性）
   - 这三层的技术实现和信任假设差异很大，不能混用

5. **AI × ZKP 的结合点（Hackathon 灵感）**：
   - zkML：证明 AI 模型真的用了某个特定模型推理，但不暴露模型权重
   - 链上 Agent 决策证明：Agent 做了什么决策、基于什么输入，用 ZKP 生成可验证证明
   - 与 Payment/Commerce 方向的交叉：用 ZKP 证明 Agent 任务已完成但隐藏交易细节

## 🚧 遇到的问题

- ZKP 的理论到工程落地有较大鸿沟：Groth16 需要可信设置，PLONK 通用但电路设计复杂。Hackathon 阶段直接写电路不现实，优先考虑用现有 ZKP 工具链（Circom + snarkjs 或 Noir）
- zkML 方向目前生态还不够成熟（EZKL / Giza 可用但上限有限），如果 Hackathon 要用，需要聚焦极简场景
