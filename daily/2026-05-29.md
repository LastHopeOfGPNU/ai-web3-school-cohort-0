### 🛡️ Week 2 任务：Wallet / Permission — Agent 链上动作权限策略

`tasks/week_2/wallet_permission.md`

系统化设计了 Agent 操作链上资产时的权限控制体系，覆盖四个层次：

**1. Agent 链上动作执行流程**
- 完整流程图：从用户任务 → 意图解析 → 模拟 → 策略校验 → 人工确认 → 链上执行 → 审计记录
- 核心设计原则：读/模拟可自动，写/转账需策略约束 + 人工确认分层

**2. 自动化 vs 人工确认的边界**

| 阶段 | 可自动化 | 必须人工确认 | 原因 |
|------|---------|-------------|------|
| 信息查询/模拟 | ✅ | — | 只读无风险 |
| 授权创建 | — | ✅ 必须 | 授权边界决定资产风险 |
| 小额低风险交易 | 白名单内可自动 | 超阈值确认 | 限制损失 |
| approve | — | ✅ 必须（禁止无限授权） | 授权风险高于单次转账 |
| 合约部署/升级 | — | ✅ 必须 | 影响长期权限 |
| 治理投票 | — | ✅ 必须 | 涉及组织决策 |

**3. DeFi 资金管理 Agent 权限策略（Arbitrum 场景）**
- 预算：单次 ≤ 500 USDC，单笔 ≤ 100 USDC，日累计 ≤ 500 USDC
- 合约：仅 Uniswap/1inch/LI.FI/Safe 白名单
- 禁止：无限 approve、delegatecall、合约部署/升级、转账到陌生地址
- 滑点：≤ 0.5%，超标人工确认
- 有效期：单次任务 ≤ 2 小时，到期自动撤销

**4. ERC-4337 × Safe × Guard/Policy 分工分析**

| 机制 | 核心价值 | 对 Agent 的意义 | 局限 |
|------|---------|---------------|------|
| ERC-4337 | 账户抽象执行框架 | session key 降重复确认、批量交易、Paymaster 代付 gas | 不自动定义业务权限策略 |
| Safe | 多签 + 组织级控制 | Agent 作为 proposer，关键交易需 owner 确认 | 需 Guard 限制 module 权限 |
| Guard/Policy | 交易级规则约束 | 合约白名单、函数限制、金额/状态检查 | 策略质量决定安全上限 |

**5. 失败处理机制**：4 级失败分类（可恢复/策略失败/链上失败/安全失败），自动重试 1 次 → 暂停 → 告警/撤销权限

**6. 最小日志字段**：task_id、pact_id、simulation_result、policy_check_result、tx_hash、before/after_balance、error_code、recovery_action 等 14 个字段

## 关键收获

1. **Agent 权限设计的核心不是"能不能"，而是"在什么条件下可以"**：不是二元的 allow/deny，而是带边界的条件授权——预算、合约、函数、金额、时间、频率，每个维度都需要策略约束。

2. **三层安全架构的分工**：ERC-4337 提供可编程账户框架（session key、批量交易）；Safe 提供组织级多签控制（Agent 是 proposer 而非 owner）；Guard/Policy 提供交易级规则约束（白名单、金额限制）。三者互补，缺一不可。

3. **Task-level Pact 是 Agent 权限最小化的关键**：单次任务级别的临时授权（有有效期、有预算上限、有合约白名单），任务结束自动撤销，避免长期权限残留。

4. **策略越细维护成本越高，策略越宽风险越大**——这是 Agent 权限设计中尚未完全解决的核心矛盾。Guard 的安全性完全取决于策略质量，写错一个白名单或漏掉一个 function selector 可能导致授权形同虚设。

5. **审计是基础设施而非事后补丁**：每个执行环节（模拟 → 策略校验 → 签名 → 上链 → 余额变化）都需要可追溯的日志记录，这是 Agent commerce 的信任基石。

## 遇到的问题
- 权限策略设计需要在"安全"和"效率"之间反复权衡：策略太严格（所有交易都人工确认）会让 Agent 失去自动化价值；策略太宽松（小额自动执行）又存在资产风险。
- Guard/Policy 的策略维护是长期工程：合约白名单需要持续更新、新协议的 function selector 需要审计、跨链场景下的策略一致性需要额外设计。
