# Week 1 学习总结：AI x Web3 的边界感

本周我对 AI x Web3 的理解从“两个热门概念叠在一起”变成了更具体的流程问题：AI 可以帮助我理解、拆解、检查和生成说明，但 Web3 里真正改变链上状态的动作，仍然要回到钱包、签名、交易、Gas 和区块浏览器这些可验证环节。

以前我会把 AI 主要理解成“能回答问题的工具”，把 Web3 理解成“钱包和区块链”。这周做完概念笔记和几个小实验后，我更明显地感受到：AI 的风险在于它可能说得很顺但不一定正确；Web3 的风险在于一旦签名或交易确认，很多结果不能简单撤销。两者结合时，最重要的不是让 agent 尽快自动行动，而是先设计清楚哪些步骤可以自动化，哪些步骤必须人工确认，哪些结果必须用链上证据复核。

## 1. 我重新理解的 AI 概念：Agent 和 Tool Use

我现在理解的 agent，不只是“会聊天的 LLM”，而是一个围绕目标行动的系统。它通常会经历几个步骤：理解任务、规划下一步、调用工具、观察工具结果，然后继续调整行动。

比如一个合约阅读 agent 可以做这些事：

- 读取一段 Solidity 代码；
- 找出权限控制、资金流、外部调用、状态变量变化；
- 生成阅读问题和风险提示；
- 给出下一步检查清单；
- 在需要时调用文件读取、测试、链上查询或区块浏览器工具。

这和单次 prompt 的区别很明显。单次 prompt 更像“问一次，答一次”；agent / workflow 更像“把任务拆成流程，每一步都有输入、输出和检查点”。但是 agent 的能力越强，越需要边界。它可以调用工具，不代表它应该拥有所有权限。特别是在 Web3 场景里，工具调用可能从“查询信息”升级到“准备交易”“提交交易”“发起支付”，风险等级完全不同。

我本周最大的变化是：不再把 tool use 当成单纯的增强能力，而是开始把它看成权限设计问题。读文件、查 ABI、查区块浏览器、执行只读 `eth_call`，这些可以比较低风险地自动化；但签名、转账、授权、写入合约，就必须有人工确认节点。

## 2. 我重新理解的 Web3 概念：交易不是普通请求

以前我容易把交易理解成“向区块链发一个请求”。现在我更倾向于把它理解成“带有身份授权、成本和不可逆后果的状态变更请求”。

一笔交易至少包含几个关键点：

| 维度 | 我的理解 |
| --- | --- |
| 身份 | 交易必须由某个账户签名，签名证明这个地址授权了这次操作。 |
| 网络 | 同一个地址或合约名在不同网络上可能完全不是一回事，所以必须确认是 Sepolia、主网还是某个 L2。 |
| 成本 | 写入链上状态通常要消耗 Gas，即使交易失败也可能花掉 Gas。 |
| 后果 | 转账、授权、合约写入一旦确认，通常不能像普通互联网操作一样找客服撤销。 |
| 证据 | 交易完成后会有 tx hash，可以在区块浏览器中检查状态、合约地址、事件日志和余额变化。 |

这也让我重新理解钱包的角色。钱包不是“资产存放的地方”，而是私钥和签名确认工具。资产记录在链上，钱包负责让用户控制地址。点击钱包弹窗里的确认按钮，本质上是在用私钥授权一个动作，所以不能把它当成普通的“下一步”按钮。

## 3. AI x Web3 交叉问题：Agent 可以发起支付吗？

我的阶段性答案是：agent 可以在受限条件下参与支付流程，但不应该无条件自主支付。

这里要区分几个动作：

| 动作 | Agent 是否适合自动做 | 原因 |
| --- | --- | --- |
| 读取价格、合约地址、ABI、区块浏览器信息 | 可以 | 这是公开信息查询，不改变链上状态。 |
| 解释交易预览、生成检查清单 | 可以 | AI 适合把复杂字段翻译成可理解的风险点。 |
| 构造候选交易参数 | 可以，但要标注来源和假设 | 参数可能错，必须让用户复核网络、地址、函数和金额。 |
| 点击钱包确认、签名、授权、转账 | 不应该自动做 | 这是账户控制权和资产风险的最终确认。 |
| 在预授权预算内发起小额支付 | 只适合在明确 policy 下做 | 需要预算上限、允许网络、允许收款方、有效期和审计日志。 |

这个问题在 `x402-caw-agent-loop` 实验里体现得比较清楚：agent 可以收到 `402 Payment Required`，解析付款要求，再通过 Pact / CAW 风格的策略层检查预算、链、合约和时间窗口。只有策略允许时，agent 才继续完成模拟支付，并且记录 settlement 和 audit。这个 demo 的重点不是“AI 想付就付”，而是“AI 只能在用户事先授权的边界里付，并且每一步可审计”。

我觉得这也是 AI x Web3 和普通 AI 应用最大的不同之一：普通 AI 出错，可能是输出一段错误文本；Web3 agent 出错，可能是发错交易、授权错合约、花掉 Gas，甚至造成资产损失。因此验证 AI 执行结果不能只看它的自然语言解释，而要回到链上证据：tx hash、区块浏览器、事件日志、授权记录、余额变化。

## 4. 本周完成的 Proof-of-Work

本周我完成并记录了几个小型学习产物，其中最能体现“低风险链上交互”的是：

- Repo 路径：`experiments/sepolia-chainlink-read`
- 网络：Ethereum Sepolia testnet
- 合约：Chainlink ETH/USD Price Feed
- 合约地址：`0x694AA1769357215DE4FAC081bf1f309aDC325306`
- 区块浏览器：<https://sepolia.etherscan.io/address/0x694AA1769357215DE4FAC081bf1f309aDC325306>
- 运行命令：`npm run read`
- 调用内容：`decimals()`、`description()`、`latestRoundData()`

这个 proof-of-work 的关键点是：它使用的是 JSON-RPC `eth_call`，属于只读调用，不会生成交易，不需要钱包签名，不消耗测试网 ETH，也没有 tx hash。这个结果反而帮助我区分了两类交互：

1. 只读查询：读取链上已有状态，适合让工具或 agent 自动执行，风险主要是数据源、网络和解释是否正确。
2. 写入交易：改变链上状态，需要钱包签名和 Gas，必须人工确认，并且执行后要用 tx hash 验证。

我还完成了 `ai-contract-reading-coach` 这个命令行学习工具，用来把 Solidity 片段或 Web3 操作意图转成“合约阅读卡”。它不是审计工具，而是帮助我形成阅读步骤：先找权限、资金流、状态变化和外部调用，再把 AI 输出当成假设回到代码里验证。

## 5. 还没解决的问题和下一步探索

我还没有真正完成一笔“由我人工确认的测试网写入交易”，所以对交易生命周期的体感还不够完整。只读 `eth_call` 帮我理解了安全查询，但还没有覆盖这些问题：

- 钱包弹窗里每个字段应该如何检查？
- 一笔交易从签名、广播、pending 到 confirmed 的过程具体怎么观察？
- 如果交易失败，Gas、错误原因和事件日志分别怎么看？
- 授权类交易完成后，如何检查 allowance，如何撤销？
- 如果 agent 参与准备交易，怎样设计最小权限 policy，避免它构造出超出用户意图的操作？

下一步我想做一个更完整的实验,在 Sepolia 上选择一个低风险合约或自己部署一个最小合约，由 AI 生成交互说明和检查清单，但最终由我在钱包里人工确认交易。完成后记录 tx hash、区块浏览器链接、钱包确认前后的截图或字段说明，再对照 AI 的预期结果检查是否一致。
